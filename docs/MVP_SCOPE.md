# MVP Scope — что вырезано и почему

Этот документ фиксирует сознательный откат от полного скелета (v2-архитектура)
к минимально работающему сценарию. Ничего не забыто — всё вырезанное здесь
перечислено явно, чтобы возвращать по одному компоненту за раз, а не
восстанавливать всё сразу «по памяти».

## Что осталось (единственный сценарий)

```
POST /documents  → parse → chunk → embed → store in ChromaDB   (синхронно)
POST /chat       → embed question → retrieve → generate → cite (синхронно)
```

Три файла реальной логики: `ingestion/parser.py`, `ingestion/chunker.py`,
`services/document_service.py`, `services/chat_service.py`. Всё остальное —
тонкая обвязка (роуты, схемы, клиент к Ollama, клиент к Chroma).

## Что вырезано и почему

| Компонент | Почему вырезан из MVP | Когда возвращать |
|---|---|---|
| Auth / Users / JWT | Не влияет на то, работает ли RAG-сценарий. Один пользователь = не нужен. | Когда появится второй реальный пользователь, не раньше. |
| PostgreSQL + SQLAlchemy-модели | Вся нужная для MVP «метадата» (document_id, filename, chunk_index) уже хранится прямо в ChromaDB. Отдельная БД добавляет миграции/модели без пользы для сценария. | Когда понадобится то, что Chroma не даёт: версии документов, пользователи, аудит. |
| Celery + Redis (Job Queue) | Обработка документа — секунды на файл среднего размера; синхронного ответа достаточно для демо и разработки. | Когда реальные файлы/конкурентные пользователи сделают синхронную обработку заметно медленной. |
| Multi-provider LLM абстракция (Ollama/OpenAI/LM Studio) | Абстракция без вторых реальных реализаций — это сложность "на будущее", которая ничего не доказывает сейчас. | Когда реально понадобится второй провайдер — тогда интерфейс появится по факту двух реализаций, а не заранее. |
| Memory (Conversation State, User Profile) | Каждый вопрос независим — это не мешает доказать, что retrieval+citation работает. | После того как заработает базовый chat — добавить историю одного диалога, потом профиль. |
| Admin / History / Search как отдельные фичи | Не часть сценария "документ → вопрос → ответ с источником". | Отдельные фичи после MVP, не блокируют его. |
| Frontend (React) | Swagger UI и curl полностью достаточны, чтобы показать, что фича работает. | Когда сценарий стабилен — тонкий UI поверх тех же двух эндпоинтов. |
| Observability / Evaluation / Security-слои из v2 | Ценны для продакшена, бесполезны для доказательства "фича работает" на одном локальном прогоне. | После MVP, вместе с возвратом остальной инфраструктуры. |

## Что не потеряно

Полная архитектура v2 и полный скелет (со всеми слоями) остаются как
референс на будущее — они не удалены, а зафиксированы отдельно (см. предыдущие
файлы проекта: `LOGICS_Architecture_v2.md`, полный `logics-skeleton.zip`).
Этот MVP — не замена архитектуре, а способ проверить самую рискованную часть
идеи (retrieval + генерация с цитированием) до того, как вкладываться в
инфраструктуру вокруг неё.

## Порядок возврата компонентов (если/когда проект снова растёт)

Если MVP отвечает на реальные вопросы по реальным документам — можно
возвращаться к `ROADMAP.md` из полной версии, но с одной поправкой: **не
восстанавливай компонент, пока для него нет конкретной причины** ("нужен
второй пользователь" — тогда auth; "нужна параллельная обработка" — тогда
Celery), а не потому что "так было в архитектуре".

Разумный порядок, если решишь расширять:
1. Простая история диалога (без резюмирования) — минимальное добавление к `/chat`.
2. Auth — как только появится второй пользователь или потребность в изоляции документов.
3. Async-обработка (Celery) — как только загрузка файла станет заметно тормозить.
4. Всё остальное — по мере реальной необходимости, не по графику.
